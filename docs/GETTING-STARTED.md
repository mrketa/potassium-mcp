# Getting Started

This guide follows the 1.1.0 source contract. Check the [releases page](https://github.com/mrketa/potassium-mcp/releases) for published downloads; a source checkout or draft is not proof of completed qualification. The [support matrix](../potassium-mcp/README.md#support-freeze-and-release-status) separates supported targets from artifact-bound evidence. No build or test count here substitutes for the selected release's receipts.

## Windows local installer

> **Full-access default:** a genuinely fresh Windows installation grants its generic `agent` read, admin, and execute access, including `potassium_execute_luau` and `potassium_execute_luau_async`. Arbitrary Luau can change the connected client and act with its executor's permissions. Connect only trusted agents; untrusted content or prompt injection may induce unwanted actions. See [Security](../SECURITY.md).

1. Start Potassium once so `%LOCALAPPDATA%\Potassium\workspace` exists. Setup needs an existing Potassium workspace; it does not install Potassium or Roblox.
2. Download the selected published version's `Setup.exe` and verify its matching checksums. Run Setup, use the directly visible **Change folder** picker if needed, then **Install**. The Windows ZIP contains the actual installer and sealed bundle, not a filtered source tree. Setup is unsigned. Unpublished candidates are for explicitly authorized qualification, not ordinary installation.
3. Use **Copy configuration**, **Copy command**, or **Copy path**. The generated `connection.json` uses the stable installed launcher with no arguments:

   ```json
   {
     "mcpServers": {
       "potassium": {
         "command": "<absolute installed path to PotassiumMcp.Launcher.exe>",
         "args": []
       }
     }
   }
   ```

   Use the actual absolute path generated by Setup, not the illustrative placeholder above. Manually merge the entry into your MCP stdio-capable harness, preserving other servers and settings; adapt the outer configuration syntax if the host requires it. A command-only host uses that executable and an empty argument list. No new host is registered automatically, and credentials are not copied into this connection entry.
4. Restart/reload the host and use **Check**. **MCP connected** means the MCP/broker path is available; **Executor not attached** is expected before a Potassium client is attached. Start Roblox and attach Potassium only after the host/broker is running. Then inspect `potassium_status`, `potassium_capabilities`, and `potassium_list_clients`; select `clientId` explicitly if several clients are attached.

There is no Desktop/CLI selection, extra Setup warning/consent/permission prompt, or Safeproxy. Full access applies only to genuinely fresh state after recovery has been resolved, not merely because a configuration file is missing. Updates, repairs, and reinstalls with retained configuration preserve explicit existing permissions, including restrictions. A missing `agent` policy in existing configuration may receive a read-only entry, never elevation of admin, execute, or the global gate. Setup does not bypass harness/application approvals. Authentication, loopback restrictions, truthful annotations, and resource limits remain active; optional HTTP/fallback transports, external hosts, and trace/artifact root access are not automatically widened.

No global Node/npm or shared .NET installation is required. The application root `%LOCALAPPDATA%\Programs\Potassium MCP` retains the launcher and a versioned Node `22.23.2`/MCP/dependency bundle after Setup closes. Private configuration, token, and artifacts stay under the separate `%LOCALAPPDATA%\Potassium\MCP` state root.

Reopen Setup for **Check**, **Repair**, or uninstall. Updates are manual: download the newer verified Setup and use **Update** with the same account and installation roots. It installs its own embedded bundle, not npm `latest`. Restart affected hosts and manually restart/reattach Potassium afterward. Repair can recover a partial installation; uninstall retains private config/token/artifacts for reinstall and requires confirmation. Existing custom wrappers and ownership conflicts are preserved and rejected rather than overwritten. See [Deployment](DEPLOYMENT.md#windows-local-installer).

## Advanced alternative: npm CLI and optional adapters

This route is independent of the Windows installer, not a selection required by its UI. Its defaults remain unchanged: the example explicitly grants read-only access, not Windows Setup's fresh full-access policy.

1. Start Potassium once so `%LOCALAPPDATA%\Potassium\workspace` exists.
2. Install the exact verified candidate tarball only for authorized qualification. Once 1.1.0 is published, ordinary installation can use `npm install --global @mrketa/potassium-mcp@1.1.0`. A manifest version alone does not establish contents; use the matching release receipt and integrity.

   ```powershell
   npm install --global <verified-candidate.tgz>
   potassium-mcp setup --workspace "$env:LOCALAPPDATA\Potassium\workspace" --read-host omp-project-a --dry-run --json
   potassium-mcp setup --workspace "$env:LOCALAPPDATA\Potassium\workspace" --read-host omp-project-a --json
   ```

3. Print a standard entry without changing any host:

   ```powershell
   potassium-mcp config print --host-id omp-project-a --json
   ```

   The setup step explicitly creates the ordinary read-only policy ID without registering an application; unknown custom IDs reject until configured. Paste the printed absolute Node/public-bin entry into the intended application. The runtime contract is `potassium-mcp serve --config <absolute-config-path> --host-id <unique-id>`. For a matching approved npm release, `config print --host-id omp-project-a --npm --json` emits a pinned npm entry.

4. Optionally let the requested adapter register that host instead:

   ```powershell
   potassium-mcp host add --host omp --host-id omp-project-a --scope project --dry-run --json
   potassium-mcp host add --host omp --host-id omp-project-a --scope project
   ```

   Adapter and policy ID differ. Use a unique ID for each project/launcher; registration does not grant policy. Implemented adapters are `omp`, `codex`, `claude-code`, `claude-desktop`, `vscode`, `cursor`, `gemini`, and `manual`, not a list of independently qualified application versions.

5. Run `potassium-mcp doctor --json`, then restart/reload changed MCP hosts. Start Roblox and attach Potassium only after a host/broker is running.
6. Read `potassium_status`, `potassium_capabilities`, and `potassium_list_clients`. Explicitly select `clientId` when more than one executor is attached; compare status counters around one bounded read. Tool discovery is not proof that the running bootstrap supports a feature.

Setup is hostless and stores private state outside npm/cache directories. npm owns the package; setup/repair deploy canonical Lua assets; `host add/remove` only change requested proven-owned registrations. `config print` and dry-run do not mutate state. `serve` never installs, deploys, or adopts credentials.

Read, admin, and execute are independent policy axes. Use `setup`/`repair` with `--read-host <id>`, `--deny-read-host <id>`, `--admin-host <id>`, or `--execute-host <id>` for intended trusted IDs; only execute needs `--allow-unsafe-execute`. HTTP has independent `--http-no-read`, `--http-admin`, and `--http-execute`. Shared-token policies are not isolation from malicious token holders, and arbitrary Luau is not sandboxed.

Enable optional `/mcp` with `--streamable-http`, `/mcp/session` with `--stateful-http`, and diagnostic-only fallback with `--builtin-fallback-token-file <private-path>`. Follow [the legacy HTTP handshake and headers](API.md#optional-streamable-http-transport); no handshake-free MCP revision or SSE replay is promised.

Use `repair` for deployment/configuration, `host remove` for one registration, and `uninstall --all` for proven-owned registrations/deployment while retaining configuration, token, artifacts, and reinstall evidence. Remove npm packages separately. Existing custom wrappers/junctions are migration conflicts to preserve, not files to overwrite; follow [the conflict procedure](../potassium-mcp/README.md#existing-installation-conflicts).

Async execution requires the global unsafe gate and the calling identity's execute permission; fresh Windows Setup supplies both for `agent`, while the advanced CLI requires explicit grants. Poll the opaque job ID for status/result and separately bounded console output; never automatically retry an indeterminate submission. Running cancellation is cooperative, not forced termination. Token rotation or bootstrap replacement requires reattach; never reload the bootstrap through its own active MCP connection.

### Optional native editor and interactions

Native desktop editor access is off by default and needs its own explicitly configured native credential, not the custom broker token. Follow [Native desktop editor configuration](CONFIGURATION.md#native-desktop-editor). The six tools list/read/open/write/activate/close tabs without Roblox. Enabling them preserves all existing host/HTTP grants and raw Luau access; it does not grant execution. Prefer new drafts. Writes require a best-effort hash precondition, not atomic native editing; dirty tabs cannot be closed.

For live interactions, first inspect `potassium_interaction_inventory` with a narrow Workspace scope and summary/rows/detail views. Reads require `interactionInventory` v1; a separately authorized `potassium_interaction_call` requires `interactionActions` v1, `asyncJobs` v2, and execute/global gates. It dispatches one click, prompt, or boolean touch and returns a job ID. Touch takes explicit BaseParts and forwards the boolean unchanged. Native dispatch is not a server acknowledgement, phase guarantee, or gameplay success. See [interaction API](API.md#one-typed-interaction-job); never automatically replay uncertain submissions.

## Selected workflow examples

1. Read status/clients and select clientId only for live work. Capabilities defaults to a short version/identity summary; use `{ "view": "full" }` for methods/limits or `{ "view": "section", "section": "resources" }` for counters. Retained inventory queries require inventory4 and new game-context capture requires gameContext2; missing versions return INCOMPATIBLE_CLIENT, not a silent fallback. Saved-map/context/source reads remain available offline.
2. Call `potassium_remote_inventory` with `{ "root": "game", "view": "summary", "limit": 20 }` (and clientId where needed). Inspect `coverage`, `stopReasons`, and parent/class groups. Take a narrower fresh scan when appropriate; partial coverage cannot prove absence.
3. Use the returned snapshotId with `view: "rows"` and selected fields. For another search of stored rows use `{ "snapshotId": "<id>", "view": "rows", "query": { "nameContains": "Shop" } }`; no new scan or snapshot is created. Original partial coverage still applies. Use includeReferences only for needed live targets, follow query-bound cursors, and release snapshots/references independently.
4. Large responses can be `kind: "potassium/result"` descriptors. Call `potassium_result_read` with one pointer or `{ "resultId": "<id>", "pointers": ["/results/0", "/results/3"], "maxBytes": 2048 }`. Auto is now the default for both: complete small selections arrive as typed values, unfinished text/pending rows carry offsets. Existing concatenating text consumers must explicitly pass `"view": "text"`. Scope/permission and120-second/eviction limits remain.
5. A selected capture call is `{ "targets": ["<selected-remote-reference>"], "durationMs": 5000, "maxEvents": 100 }`; poll its captureId summary/events and stop. This observes only outbound namecall metadata, never values/returns or calls manufactured by capture. Native game interception remains unverified, including foreign-hook limitations.

For before/after state plus selected remote metadata, call `potassium_observe_action` with `{ "operation": "start", "requests": [{ "path": "<state-reference>", "properties": ["Value"] }], "remotes": ["<remote-reference>"], "durationMs": 5000 }`. Perform the separate action during the window, then poll/stop using the returned observationId. Stop may return completing; poll obtains terminal coverage/diffs. Correlation is temporal, not causal, and the observer performs no automatic game/UI action.

The separate typed call helper takes one selected target: `{ "target": "<echo-reference>", "method": "InvokeServer", "arguments": ["sample", null, { "type": "Vector3", "x": 1, "y": 2, "z": 3 }] }`. It returns an async jobId for the normal job status/result/console/cancel tools. Capture/observation/calls require execute/global gates. Queued cancellation sends nothing; after dispatch it cannot interrupt native InvokeServer and preserves eventual values/errors. FireServer completion reports local dispatch, serverAcknowledged false. No blind bulk-discovery invocation/replay occurs.

Focused read-policy examples are `potassium_diagnostic_snapshot` with `{ "view": "character" }`, `{ "view": "ui", "root": "player_gui", "limit": 5 }`, or `{ "view": "nearby", "radius": 24, "limit": 5 }`. They report coverage/truncation and issue stable references; overview remains unchanged. `potassium_session_stats` with `{}` reports bounded metadata-only calls/bytes/timing/detail reads/repeated selections, not arguments, data, or token counts; its current call is already in-flight in that snapshot.

For file-backed traces, use `potassium_trace_summary` first (rows omitted by default), then a filtered `potassium_trace_query`, then a result pointer such as `/rows/0` if the query is compacted. Queries default to 20 rows/8192 bytes; artifact reads default to 4096 bytes. Check bounded coverage indicators rather than treating a summary as the entire file.

Ordinary hosts keep the full catalog. Only clients implementing the explicit vendor negotiation should opt into lazy discovery, search/activate named typed tools with `potassium_tool_catalog`, and refresh tools/list on list changes. Follow every standard nextCursor; SDK 1.30.0 listTools/auto-refresh fetch only one page and cache that page's validators. See [API](API.md#catalog-discovery-and-activation) before implementing a paged client. No permissions, host registration, or Setup defaults change.

## Share one game snapshot across agents

With Roblox attached, call `potassium_game_context` with `{ "view": "capture", "root": "workspace", "screenshot": true, "map": true }`. The response gives a shared contextId, timestamp, coverage and image availability; it does not dump the whole scene or image bytes immediately.

Give that contextId to other agents. They can read summary, `"section": "parts"`, `"section": "ui"` or `"section": "remotes"` and follow nextOffset, or request `{ "view": "image", "contextId": "<id>", "kind": "screenshot" }` / `"kind": "map"`. List finds saved snapshots; release removes one. These views work with Roblox closed and across read-authorized sessions using the same config. Remote collection defaults to50 identities from ReplicatedStorage, shares capture budgets and never invokes them; remoteLimit0 excludes it explicitly.

Read `limit` counts rows (1..100, default20), not bytes; pages also obey the response byte budget. New gameContext2 captures reserve separate facet shares within the aggregate work/visit/byte limits. Every facet can still be partial; inspect its counts/stopReasons rather than assuming a complete map or UI/remote set.

The screenshot requires an unambiguous visible Roblox window and never falls back to the desktop. Unavailable images are explicit; valid scene data remains usable. The map is a labeled top-down projection of loaded boxes, not complete map geometry or navigation. Captures do not move the camera/player or invoke remotes. Saved data stays static; capture again only when needed, instead of having every agent rescan.

## Reconstruct and share a parkour map

Call `potassium_map_context` with view build and contextIds containing saved game snapshots. No attached client is needed. The result contains a mapId, revision, source scope, counts and uncertainty. Read parts/surfaces/chunks through `potassium_map_geometry`, links/routes through `potassium_map_navigation`, and tracks/hazards through `potassium_map_motion`. All agents use the same immutable revision instead of rescanning the game.

Use view update with mapId and newly saved contextIds to extend observed regions. The returned mapId is a new parent-linked revision; preserve the parent if another agent still needs it. Missing objects in a partial capture are not treated as deleted, and unknown/unloaded space is not considered empty.

For a normally attached gameContext2 client, view observe selects MapPart IDs carrying still-valid native snapshot/object bindings. Expired or older path-only data cannot be rebound. View probe adds a bounded downward ray grid for uncertain surface geometry. These operations only observe; they do not move the player/camera, invoke remotes, test deaths deliberately or traverse the parkour.

Management view image draws a bounded layer-aware graph using optional minY/maxY. `potassium_map_navigation` view route takes mapId/from/to surface IDs and returns modeled actions without executing them; allowUncertain defaults false. Assumed profiles, approximate support, unknown collision eligibility or motion/hazard uncertainty can prevent a modeled route. Recorded timing is not a guarantee of safety in the current live game.

For explicitly reported floor/ceiling behavior, use `potassium_map_mechanics` view apply with the saved mapId, supportModes and a complete transition list. Bind each report to an exact retained partId and state its direction/note; do not infer behavior from ReversePad names. Apply creates a new revision using retained sources, even after the original captures are released. Read view returns the reports and provenance. A mode-switch route is a candidate itinerary with unknown/null transfer timing, not a measured gravity trajectory or execution command.

## Offline supplied-source analysis

No executor is needed for read-policy index/query. Build the Windows x64 native worker with `node tools/native-parser.mjs build` (hash-pinned Zig `0.14.1` provisioning at build time), then the self-contained controller with `node tools/parser-host.mjs build`, before packaging/Windows stage/build. Production uses native C Tree-sitter `0.25.0`/Luau grammar `1.2.0` under ordinary no-capability AppContainer/atomic Job limits; no private desktop/station or existing UI ACL edits. The trusted parent validates returned tree data and runs bounded semantic analysis. Web-tree-sitter/WASM are development-test-only, never runtime fallback. [Build prerequisites](DEPLOYMENT.md#building-the-local-windows-artifact) and [OS qualification](TESTING.md#workflow-expansion-source-qualification) are separate from parser correctness; unavailable backends fail explicitly.

Call `potassium_code_index` with inline modules, for example `{ "modules": [{ "id": "Client", "source": "local function send(remote, payload)\n  return remote:InvokeServer(payload)\nend\nreturn send" }], "provenance": "supplied-example" }`. Use its returned indexId in `{ "indexId": "<returned-indexId>", "view": "calls", "query": "InvokeServer" }`, then a returned call `id` in `{ "indexId": "<returned-indexId>", "view": "origins", "callsiteId": "<returned-call-id>", "depth": 4 }`. Origin uncertainty is explicit; method spelling alone is not remote/server identity. View source requires moduleId and returns redacted excerpts, not wholesale raw source.

Explicit-file intake replaces source with `"root": "sources", "path": "Client.luau"`. Only fresh configuration initializes `<workspace>/potassium-mcp-sources`; existing configs are not widened, and inline intake needs no roots. `sourceRoots` is separate from artifacts and requires trusted root ownership. No recursive scanning, imports/downloads, execution, or server-source reconstruction occurs. Release with `{ "indexId": "<returned-indexId>", "view": "release" }`; indexes otherwise expire after ten minutes or earlier bounded eviction. [API](API.md#offline-luau-source-index) documents all schemas, paging, redaction, and limits.
